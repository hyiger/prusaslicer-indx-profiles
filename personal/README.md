# Personal filament presets

Not part of the generated set. These are exports from the author's own
[Filament DB](https://github.com/hyiger/filament-db) app — see the `# PrusaSlicer
config bundle generated by Filament DB` header on each file — for filaments Prusa
does not publish an INDX profile for. They are kept here because they are useful,
not because they are derived from anything in `PrusaResearch.ini`, and none of the
provenance discipline in `../CLAUDE.md` applies to them.

**They do import** — but two of their keys mean nothing to stock PrusaSlicer:

| Key | Where it comes from |
|---|---|
| `activate_air_filtration` | an Orca/Bambu key with no PrusaSlicer equivalent |
| `filamentdb_id` | only exists in the [Filament Edition fork](https://github.com/hyiger/PrusaSlicer) |

Neither stops an import. `PresetBundle::load_configbundle` does call
`set_deserialize` with no per-key `try` (`PresetBundle.cpp:1609`, rethrowing at
1625), but the throw is never reached: `PrintConfigDef::handle_legacy` clears
any key the config definition does not have (`PrintConfig.cpp:5377-5380`, a
catch-all after the `PrintConfigDef_ignore` list at 5372) and
`set_deserialize_nothrow` returns early on an empty key (`Config.cpp:484-495`),
before the `UnknownOptionException` at `Config.cpp:531` is reachable. Prusa's
own `PrusaResearch.ini` relies on this: it carries a misspelled
`top solid_infill_speed` in `*INDX_025_common*` and loads at startup regardless.

So **File → Import → Import Config Bundle** is the route to use. It is also
better than installing by hand: with `SaveImported` the preset is written back
out as a flat file in `<datadir>/filament/`, and it is named from the section
header (`SunLu PP`) rather than from the filename stem (`SunLu_PP`).

**What you must not do is drop one into `<datadir>/filament/` unchanged.** That
path is `ConfigBase::load_from_ini` → `read_ini` → `ConfigBase::load(tree)`, and
`ConfigBase::load` iterates only the *top level* of the tree
(`Config.cpp:741-751` at `version_2.9.6`). `read_ini` nests every key one level
down under the `[filament:…]` section, so the loop sees a single node named
`filament:<Name>`, fails to recognize it, ignores it, and applies **no keys at
all**. `load_presets` then lays that empty config over PrusaSlicer's defaults, so
you get a preset named after the file with every value at the compiled-in
default — nozzle 200 °C, bed 0 °C — and nothing is logged. It is the same trap
`../CLAUDE.md` documents under "User preset files on disk must be fully
flattened", and for a PC, TPU or PP preset it is a silently wrong print.

If you do want to install one by hand, delete the `[filament:<Name>]` header
line so the keys sit at the top level, and name the file `<Name>.ini` —
`load_presets` takes the preset name from the filename stem, spaces included.
Each export is already fully flattened, so every real key then applies.

Tidying the exporter would still be worth doing — stop emitting
`activate_air_filtration`, and emit `filamentdb_id` only for the fork — but
neither key costs anything today beyond a line PrusaSlicer throws away. Do not
hand-edit these files: they are regenerated by that app, and an edit here is
lost on the next export.
